# club-rank

A ranking system for student clubs, modelled on ICC player rankings: clubs are scored
across weighted criteria so that project quality counts more than project quantity.

- **Backend** — Go 1.23, Gin, GORM, PostgreSQL, Swagger
- **Frontend** — React 18 + TypeScript + Vite, Tailwind + shadcn/ui, Clerk auth

Work in progress. See [Status](#status) for what is and is not built.

## Data model

Defined in `backend/migrations/001_create_tables.sql`:

| Table | Purpose |
| --- | --- |
| `users` | People, with a role: `super_admin`, `club_admin`, `tech_head`. `club_id` links a user to a club. |
| `clubs` | A club: name, logo, subdomain. |
| `domains` | A unit inside a club (e.g. a team or sub-domain). Belongs to a club. |
| `students` | Students, each assigned to one domain. `reg_no` is unique and must match `^RA[0-9]{13}$`. |
| `scores` | One monthly score per student per domain. |

## How a ranking is calculated

Implemented in `backend/services/ranking_service.go`.

1. `POST /api/rankings/calculate/:clubId` loads the club's domains and the ranking criteria.
2. For each domain, every student in it gets a **student score**: the average of the
   last 3 months weighted `0.7`, plus the average of everything older weighted `0.3`.
3. A student with fewer than 3 scores total is **inactive** and does not count toward
   the domain average.
4. The domain score is the average of its active students' scores, multiplied by the
   criterion's `Weight`.
5. Domain scores are summed into one club score, stored as a `Ranking` row.

`GET /api/rankings` returns the stored rankings with each club's name and a rank
number, assigned by row order.

## Backend setup

### 1. PostgreSQL

Create the database and user (see `Commands.text`):

```bash
sudo service postgresql start
sudo -u postgres createdb club_rank
sudo -u postgres createuser -P aswath
sudo -u postgres psql -c "GRANT ALL PRIVILEGES ON DATABASE club_rank TO aswath;"
```

### 2. Apply the schema

`backend/config/config.go` connects with GORM but does **not** run migrations, so the
tables must be created yourself:

```bash
psql -h <host> -U aswath -d club_rank -f backend/migrations/001_create_tables.sql
```

### 3. Point the app at your database

The DSN is currently a hardcoded literal in `backend/config/config.go`:

```go
dsn := "host=172.27.132.255 user=aswath password='1234' dbname=club_rank port=5432 sslmode=disable"
```

Edit that line to match your own host and password. There is no environment variable for
it yet.

### 4. Run

```bash
cd backend
go mod download
go run ./cmd
```

The server listens on `:8080`.

| URL | What |
| --- | --- |
| `http://localhost:8080/health` | Health check — public |
| `http://localhost:8080/swagger/index.html` | Swagger UI — public |
| `http://localhost:8080/swagger.yaml` | OpenAPI spec — public |
| `http://localhost:8080/api/*` | All resource routes |

### API routes

Everything under `/api` goes through `middleware.Auth()`.

```
GET    /health

GET    /api/users                  POST   /api/users
GET    /api/users/:id              PUT    /api/users/:id
DELETE /api/users/:id

POST   /api/clubs                  GET    /api/clubs
PUT    /api/clubs/:id              DELETE /api/clubs/:id
GET    /api/clubs/:id
GET    /api/clubs/:id/domains

POST   /api/domains                GET    /api/domains
GET    /api/domains/:id            PUT    /api/domains/:id
DELETE /api/domains/:id

POST   /api/rankings/calculate/:clubId
GET    /api/rankings
GET    /api/rankings/criteria      PUT    /api/rankings/criteria
```

Full request and response schemas are in the Swagger UI — the source of truth is
`backend/docs/swagger.json`, generated by swaggo from the `@Description` annotations on
the models in `backend/models/`.

### Tests

```bash
cd backend
go test ./...
```

Integration tests live in `backend/tests/integrations/`. They read their connection
settings from `TEST_DB_HOST`, `TEST_DB_USER`, `TEST_DB_PASSWORD`, `TEST_DB_NAME`, and
`TEST_DB_PORT` (see `backend/config/config_test.go`), falling back to the same
hardcoded local values if unset. **They hit a real database — they are not isolated
from it.**

## Frontend setup

```bash
cd frontend
npm install
```

Create `frontend/.env.local` with your Clerk publishable key:

```
VITE_CLERK_PUBLISHABLE_KEY=pk_test_...
```

`frontend/src/main.tsx` throws on startup if this variable is missing.

```bash
npm run dev      # dev server
npm run build    # tsc && vite build
npm run lint
npm run preview
```

## Status

Built and working:

- Layered backend (controller → service → repository) over GORM/PostgreSQL
- CRUD for users, clubs, domains; ranking calculation and criteria endpoints
- Swagger docs served from the running server
- Vite + React + Tailwind + shadcn/ui frontend scaffold with Clerk sign-in/sign-up

Not built yet, despite what the planning docs describe:

- **Authentication is a stub.** `backend/middleware.Auth()` calls `ctx.Next()` and does
  nothing else, so every `/api` route is currently open. JWT is described in
  `Instructions.md` but not implemented.
- **Score repository is never wired in.** `NewRankingService` leaves `scoreRepo` nil, so
  `calculateStudentScore` fails and every domain scores 0.
- **No Web3.** `Instructions.md` plans on-chain immutable rankings and end-of-semester
  tokens. No Solidity contract or blockchain integration exists in this repo.
- **No student or score endpoints.** The models and tables exist, but no routes expose them.
- **Frontend is minimal.** Only `/clubs` is wired up behind `SignedIn`; `Home`,
  `RankingPage`, `LoginPage` and `StudentRanking` exist but are not routed.
  `frontend/src/App.tsx` also reads `process.env.REACT_APP_CLERK_FRONTEND_API`, which Vite
  does not populate — `main.tsx` already wraps the app in `ClerkProvider`, so the nested
  provider in `App.tsx` is redundant.
- **No deployment setup** (Docker, CI, Railway/Heroku config).
